# Fastfood Kitchen 项目盘点与重开评估

生成日期：2026-08-06

## 一、项目定位与业务模式

**定位**：称重式快餐连锁门店（荤素同价、按两计价、米饭另计费）的内部管理平台，覆盖「菜品规划 → 备料 → 成本核算 → 经营分析 → 采购」全链路。

**服务对象**（8 角色）：admin（管理员）、chef_manager（厨师长）、chef（厨师）、prep（备料员）、breakfast_chef（早餐主厨）、breakfast_assistant（早餐帮工）、buyer（采购）、store_manager（门店经理）。

**核心业务假设**：
- 每日菜单由厨师长在推荐算法辅助下快速定稿
- 推荐算法用经营数据（客单价、剩余反馈）动态调优
- 出餐按工位（炒锅/煎扒蒸菜/切配/早餐炒锅/早餐副手）分工
- 采购应从已发布菜单反算需求量（尚未实现）

## 三、设计目的（核心决策为何存在）

| 设计 | 目的 |
|---|---|
| 8 角色 + 5 工位双维度权限 | 后厨真实分工（厨师长定菜单、厨师出餐、备料员备料、店长填报）；工位过滤菜品降低噪音 |
| 前端过滤工位（API 不筛） | 减少 API 调用次数，JWT 携带 station 直接前端过滤 |
| 多维度推荐算法 | 把经验菜单决策变成可解释的数据决策（客单价反馈/搭配缺口/剩余反馈/多样性/毛利） |
| 4 维度菜单评分 | 厨师长选菜后即时可见完整度/多样性/新鲜度/毛利结构，形成改进闭环 |
| 早餐审核流 | 早餐角色改菜需 admin/chef_manager 审核（P1 新增权限设计） |
| 补单 | 出餐中的临时加菜不污染正式菜单计划 |
| 操作日志 | 多角色协作下的责任追溯 |
| 门店隔离 + 算法参数可调 | 不同门店定价/消费水平不同，参数按门店隔离 |
| sql.js 开发 / Postgres 生产 | 开发零依赖快速启动，生产走迁移 |

## 五、重开评估

### 重开前必须先回答的问题
1. **动机是什么？** 代码质量不满意 / 技术栈要换 / 需求大幅变化 / 想让系统更简单？
2. **保留什么？** 业务模型（角色/工位/推荐算法/数据）是否继续用？
3. **谁用、何时用？** 上线时间压力决定是重开还是修补。

### 三条路径对比

| 路径 | 工作量 | 风险 | 适用场景 |
|---|---|---|---|
| **A. 重开（推倒重写）** | 2.8 万行 × 熟练度系数；全栈双前端+后端 ≈ 1.5-3 个月全职 | 高：新代码新 bug、业务细节易丢（P1 算法 900 行打磨过的逻辑重写即回归） | 技术栈必须换（如不用 Taro）或代码质量已不可维护 |
| **B. 渐进式重构（推荐）** | 2-4 周分阶段 | 低：每步可验证 | 代码质量是主因；保留业务模型与数据 |
| **C. 维持 + 补测试** | 1 周打底 | 低 | 急着上线，先稳住 |

### 我的判断：**不建议推倒重开**，理由：

1. **2.8 万行已实现且通过真实 Postgres 验证**——重写时间成本远高于修复。业务逻辑的 80% 是"数据增删改查 + 权限 + 算法"，重写后还要重验一遍。
2. **最有价值的部分（推荐算法、菜单评分、审核流、补单）恰恰是重写最易出错的部分**——P1 算法 900+ 行，含 5 类加成和评分引擎，重写 = 白付一轮调试成本。
3. **真正的痛点不是代码质量，而是缺测试和缺规范**——这通过 B 路径可低成本解决。
4. 若重开的真实动机是「感觉太复杂/太重」，那正确的方向是**砍功能 + 简化架构**（如合并模块、减少配置页），而不是重写。

### 若坚持重开，最小可行重开方案
1. 保留：数据库 schema（8 个迁移不动）、种子数据、PLAN-P1/PLAN-P2 设计文档
2. 重写：API 采用模块化更彻底的骨架（DTO 全覆盖 + 测试先行）；web-admin 维持 Next.js；**miniapp 升级 Taro 4 或换 uni-app**（消除 webpack 兼容债）
3. 先写 3 个验收场景再动工：登录→菜单规划→发布；填报→次日推荐调整；成本→毛利链路
